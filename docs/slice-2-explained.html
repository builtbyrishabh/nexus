Ground floor

Where we were at the end of Slice 1

To see what Slice 2 changes, hold the old pipeline in your head. When someone asks a question, retrieve() did four things, in order:

  1. Dense search — find chunks whose meaning is close to the question (vector similarity). Top 20.
  2. Sparse search — find chunks that share exact words with the question (full-text). Top 20.
  3. RRF fusion — merge the two lists into one ranking. But RRF only sees rank positions — "this chunk was #2 in dense and #5 in sparse." It never reads the actual text.
  4. Neighbor expansion — widen each survivor with the chunk just before and after it (±1), for context.

That last point is the gap. RRF is fast and cheap, but it's blind to content. It's like a librarian who ranks books by which shelves they came from — never opening a single one.

Pillar 1 · Reranking

Opening the books

A reranker (a "cross-encoder") is a model that takes the question and one chunk's full text together, and scores how relevant that chunk truly is. It reads. Because it reads, it catches relevance that the fast retrievers missed.

The trade-off is cost: reading every chunk in the database would be far too slow. So the reranker only ever sees a small pool — the 20 candidates that dense + sparse + RRF already narrowed down to. Fast retrievers cast a wide net; the reranker carefully sorts what they caught. That's why it slots in after fusion and before we cut to the final few.

The one new function

Everything about reranking lives in one small, honest function. Here is exactly what it takes and what it hands back:

rerankDocuments() src/server/retrieval/rerank.ts
Takes in
query: string docs: { id, text }[] topN: number

The question, the pool of candidate chunks (id + full text), and how many to keep.

→
Gives back
RankedId[] = { id, score }[]

The topN most relevant chunk ids, best first, each with a fresh relevance score from the model.

Under the hood it calls the AI SDK's native rerank() through the Vercel AI Gateway (the same credential used for embeddings and generation — one door for every model). The default reranker is cohere/rerank-v3.5, set by one env knob, RERANK_MODEL.

One subtlety, handled by a tiny helper called mapRanking(): the model doesn't know our chunk ids. It ranks the documents array we handed it and returns positions like "item #3 is best." Since we fed it texts in a known id order, mapRanking just translates those positions back into chunk ids. Out-of-range positions are dropped defensively — retrieval must never throw.

Where it slots into the pipeline

The reranker doesn't replace anything — it's inserted as one new stage. Same inputs, same outputs at the boundary; only the middle got smarter.

retrieve() — the highlighted stage is the only thing Slice 2 inserts

Off by default — on purpose

Here's the interesting design choice. Reranking is disabled by default (RERANK_ENABLED=false). Two reasons:

  • No silent changes. Until you flip the switch, retrieve() behaves exactly as it did in Slice 1. Nothing about the shipped product moved.
  • Measured, not asserted. Everyone believes reranking helps. We wanted to prove it on our own data. So retrieve() accepts a per-call override — retrieve(query, { rerank: true }) — which lets the eval harness run the exact same questions both ways and read the difference.

Which is the perfect handoff to the second pillar. You can't say "better" until you can measure it.

Pillar 2 · Evals

Proving it

An eval is a repeatable exam for the whole answer path. It has three parts, and they map exactly onto how you'd grade any exam: a fixed set of questions, a strict grader, and a pass bar.

1 · The questions — the "golden set"

A hand-written list of questions with known-correct behavior, in evals/golden.ts. It grades against the Slice 0/1 stand-in corpus (Steve Jobs' 2005 Stanford commencement speech). There are two kinds of question, and that split is the whole point:

Answerable · 8 cases

What did dropping out let him study, and how did it shape the Mac?

How does he describe being fired from Apple?

How does thinking about death help him decide?

The corpus covers these. We grade the answer's quality.

Refusal · 3 cases

What are his thoughts on Bitcoin?

What's his recipe for lasagna?

What does he say about Android?

Not in the corpus. The only correct answer is to refuse.

The refusal cases exist because, for this product, the refusal is the product. A RAG bot that confidently makes things up is worse than useless. So the exam deliberately includes traps — questions the corpus can't answer — and checks that the bot declines rather than hallucinates. Its one true line:

"He doesn't cover that in his videos."

2 · The grader — three axes + one gate

For answerable questions, we use Mastra's built-in LLM-judge scorers (native — we write no grading prompts of our own). A separate judge model, EVAL_MODEL, reads the answer and scores it on three axes, each from 0 to 1. Refusal cases are graded differently: not on prose, but on the decision — did it refuse exactly when it should have?

What it checksThe question it asksPass bar
Faithfulness Are the answer's claims actually supported by the retrieved text? (the hallucination guard) ≥ 0.70
Answer relevancy Does the answer actually address the question that was asked? ≥ 0.70
Context precision Was the retrieved evidence relevant, and ranked relevant-first? (this is the axis reranking should lift) ≥ 0.60
Refusal accuracy Did it refuse on exactly the out-of-corpus questions — no more, no less? = 1.00

Refusal accuracy must be a perfect 1.00 — the only bar that isn't a "good enough" threshold. The refusal is the product, so it has to be exact: answering a trap or wrongly refusing a real question both fail the run.

The grading function

Like the reranker, the grading is one clean function. It takes what the model was asked, what it said, and the exact evidence it was given — and returns three numbers:

scoreAnswer() src/server/evals/score.ts
Takes in
query: string answer: string contextTexts: string[]

The question, the model's answer, and the exact evidence texts it read — so grading judges what it actually saw.

→
Gives back

Three scores in [0, 1], one per axis above.

3 · The harness — and why it grades the REAL path

Tying it together, runCase() runs one golden question through the exact same code production uses. This is the detail that makes the whole exam trustworthy — it doesn't test a look-alike, it tests the real thing:

  1. Call the real retrieve() (with rerank on or off — the variable under test).
  2. If retrieval finds nothing, emit the refusal directly — exactly as ask() does for real users.
  3. Otherwise, build the answer with buildAnswerMessages() — the same prompt builder ask() uses — and let the real agent answer.
  4. Detect whether it refused. If it answered, grade it with scoreAnswer(). If it refused, record only the decision.

Then summarize() — a pure, dependency-free function — averages each axis over the answerable cases, computes refusal accuracy over all cases, and checks every score against its bar. Its passed boolean is the tier gate: "don't advance a tier until its evals pass."

Running it

Three modes, one command. The first two gate via exit code — a failing run returns non-zero, so CI can block a merge. The third measures the reranker's lift directly:

pnpm evalBaseline retrieval, rerank off. Gates the build.
pnpm eval --rerankSame exam, rerank on. Gates the build.
pnpm eval --compareRuns both, prints the rerank lift (on − off). Informational.

That --compare mode is the payoff of Pillar 1's "off by default" choice: it runs the identical golden set twice and prints the per-axis difference, so the reranker's value is a number you can read — not a claim you have to trust.

Housekeeping · DRY

Two things moved so they'd stop repeating

Slice 2 also did small cleanups so nothing important is written twice (the project's DRY / "easier to change" rule):

  • The refusal string + the prompt builder → answer.ts. The refusal text and buildAnswerMessages() now live in one place, read by three callers: the agent's instructions, the live ask() path, and the eval harness. One string, three readers — so they can never drift. It also means the eval grades the real refusal, byte-for-byte.
  • The concurrency helper → util/pool.ts. A tiny mapPool() (run N tasks at a time) was extracted so both the ingest contextualizer and the eval runner share one bounded-concurrency implementation.
