Where we started

From a starter chat to a product

Before this PR, the web surface was the T3 starter's single page hitting /api/chat. It could stream one grounded answer, but there was no sign-in, no notion of a user, and nothing was saved: reload the tab and the conversation was gone. The RAG engine (retrieve → cite → refuse-or-answer) was already solid from Slices 0–3; what was missing was a place to live.

Slice 5 builds that place, modeled on the LessonPlay chat pattern, in four moves — and takes deliberate care that none of them touch the meaning of an answer:

  • Auth (Clerk). Everything except the landing redirect and the sign-in / sign-up pages is behind auth. The signed-in userId becomes the scope key for all data.
  • The chat SPA. A sidebar of past chats plus one always-mounted conversation page. Switching chats is instant because it never leaves the page.
  • Persistence. Mastra Memory on the same Postgres stores threads and messages — including each answer's citations, so [n] deep-links survive a reload.
  • The Panel, under the shell. The Slice 4 fan-out (one question → each creator's own answer) becomes a real page in the app.

The one line to hold onto: Mastra Memory is used as a store, not as agent memory. Generation still sees only the current question and its retrieved evidence. History is for the sidebar — never an input to the model. Every design choice below serves that boundary.

The map

One turn, end to end

Hold this picture while reading the code. A message from the client carries only the newest question plus a threadId. It hits the one streaming route, which runs the same ask() every surface uses, streams citations then text back, and — only for the main chat — persists the turn afterward. History for the sidebar is read separately, over tRPC.

How it works

The four moves, in detail

1 · Auth is one boundary, one identity

Clerk's clerkMiddleware calls auth.protect() for every route that isn't public. The same auth() helper is read in two more places: the tRPC context and the chat route. That single userId is the app's whole notion of "who" — it becomes Mastra Memory's resourceId, which is how a user only ever sees their own threads. There is no separate users table and no session plumbing to maintain.

2 · The SPA switches threads without leaving the page

This is the LessonPlay pattern. One /chats page is always mounted; the active thread is just a query param. Because the flip is shallow (nuqs default), selecting a chat in the sidebar doesn't trigger a route change, an RSC round-trip, or a remount — it's instant. Each conversation is keyed by its threadId, so switching mounts a fresh useChat with its own stream while the page frame stays exactly where it is.

The transport — client sends

prepareSendMessagesRequest:
  ({ messages, id, body }) => ({
    body: {
      message: messages.at(-1),
      threadId: id,
      ...body,
    },
  })

Why it matters

// Only the NEWEST message goes
// over the wire. The full history
// lives in Mastra Memory, keyed
// by threadId — nothing to
// re-upload, and the client can't
// spoof a longer "history".

3 · Memory is the store, never a model input

A completed turn is persisted after it has streamed: the plain user question, and the assistant answer with its citations attached as a data part. Storing the plain question (not the evidence-stuffed prompt the model actually saw) is deliberate — it keeps the history clean for display, and it means a reloaded thread rehydrates with working [n] deep-links (verified with a live round-trip against Neon). Crucially, that stored history is only ever read back to paint the sidebar and rehydrate a thread. It is never fed into retrieve() or the generation prompt.

Why go to this trouble? Because Nexus's promise is that every answer is grounded in what the creator actually said, on this question alone. Conversational memory would let turn N-1 bleed into turn N's retrieval and wording — exactly the kind of ungrounded drift the product refuses to allow. Titles come from the first question deterministically, with no extra LLM call, for the same reason: keep the model on the one job it's trusted to do.

4 · The Panel rides the same rails

The Panel is one question box that fans out to a column per creator. Each column is its own useChat posting to the same /api/chat route, tagged with a creatorHandle that scopes retrieval and specializes the refusal to that creator's name. Columns retrieve, cite, and refuse independently — markers never cross columns — and nothing is persisted, because the Panel is ephemeral by design. It reuses the exact same ask() and AnswerText renderer as the main chat, so a citation looks and behaves identically wherever it appears.

Load-bearing decisions

The choices worth understanding before you approve

These are the decisions that shape everything else. If any one of them is wrong for where the product is headed, this is the cheapest moment to say so.

DecisionWhat & why
core
Memory as store only, not agent memory		 The store is registered on mastra but never attached to nexusAgent. Generation stays single-turn and grounded on the current question's evidence only. This preserves the product's whole trust proposition; it is the non-goal the issue explicitly names.
core
One threads.ts module, two callers		 The streaming route and the tRPC router both call the same persistence functions — no second copy of the contract to drift. DRY, and it means "how a thread is stored" has exactly one definition.
spa
Client-minted UUID thread ids		 The id is generated up front with crypto.randomUUID, so a brand-new chat has a stable id before its first turn ever persists. That's what lets the ?id= flip be shallow and instant, and what lets optimistic sidebar updates point at a real id.
spa
Newest-message-only transport		 The client uploads only the latest question + threadId; history lives server-side. Less bandwidth, and the client can't fabricate a longer conversation than what's stored.
store
Persist the plain question, with citations		 Store what the user typed (not the evidence-stuffed prompt) plus the answer's citations as a data part, so a reloaded thread rehydrates with working [n] deep-links. Verified against the live DB before shipping.
auth
Ownership via resourceId = userId		 assertOwnership returns null for a not-yet-created thread but throws NOT_FOUND when a thread exists under another user — so an id can never be probed across users. Writes into someone else's thread throw FORBIDDEN.
auth
CLERK_* optional in env.js		 A fresh checkout without Clerk keys still typechecks, tests, and builds. The app can't actually run without them, but nobody is blocked from working on the rest of the repo.
resilience
Best-effort persist after streaming		 The answer streams first; the turn is saved afterward inside a try/catch. A store failure logs and is swallowed — it must never fail a response the user already saw.
panel
creator_handle as a column + code constant		 The creator roster is a slug on source plus a display-name constant, not a creator table. Slice 4 needs nothing more; the table can arrive when the community bot (#14) needs per-tenant rows. ETC — cheaper to add later than to carry unused now.
panel
Deterministic titles, per-creator refusals		 Thread titles derive from the first question (no extra LLM call, unlike LessonPlay's auto-title). Refusals are specialized per creator by name, using neutral "their" — we never infer a pronoun from a name.
