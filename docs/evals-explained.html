First principles

There is no answer key. The judge checks properties, not correctness.

The first thing to unlearn: the golden set does not store the "right answer" to any question. It stores questions, and for each question one bit: should Nexus answer this, or refuse? Everything else is judged by a second model looking at three properties of what came out.

InputA golden caseA question, plus whether the corpus covers it.golden.ts
Step 1RetrieveThe real hybrid retriever, top 5, rerank on or off.retrieve.ts
Step 2GenerateThe real Nexus agent, the real prompt.run.ts · answer.ts
Step 3Did it refuse?Exact match against the one refusal sentence.answer.ts
Step 4Judge ×3Faithfulness · relevancy · context precision, each 0 to 1.score.ts → @mastra/evals
Step 5Aggregate + gateMeans over answerable cases, refusal accuracy over all, compare to bars.summary.ts
OutputExit 0 or 1CI can block a tier on it.scripts/eval.ts

The four things being measured

  • Faithfulness. Take every claim in the answer. Is each one supported by the evidence the model was shown? Fraction supported. This is the hallucination guard.
  • Answer relevancy. Take every statement in the answer. Does each one actually address the question? Fraction relevant, with partial credit for "sort of".
  • Context precision. Look at the five evidence chunks in the order they were ranked. Which were useful for producing this answer? Score rewards useful chunks near the top. This is the only axis that grades retrieval, and so the only one the reranker can move.
  • Refusal accuracy. Not a Mastra scorer. Our own binary check: did the model refuse exactly on the cases marked out-of-corpus? Must be perfect.

Why this design and not a gold answer

Comparing free text to a reference answer is brittle: two correct answers can share no words, and a paraphrase check needs its own judge anyway. Faithfulness sidesteps the whole problem. If every claim is traceable to a transcript chunk, the answer cannot be invented, and the transcript is the ground truth we care about.

The cost of that choice is honest and shown on the last slide: a faithful answer to the wrong chunk scores well on faithfulness. Context precision exists to catch that, and the refusal check exists to catch the case where the model should have said nothing at all.

The note field on each golden case (for example "Reed calligraphy class → typography in the first Macintosh") is read by humans only. No code touches it.

ours entry point

pnpm eval is three lines of plumbing glue

tsx runs a TypeScript file directly under Node. There is no Next.js server in the loop, so nothing has loaded environment variables yet. That is why the very first import in the script, L1, is the env loader, and why it must stay first: the later imports pull in src/env.js, which validates DATABASE_URL and friends at import time and would throw on an empty environment.

The order of the two config() calls matters in a non-obvious way. dotenv never overwrites a variable that is already set. So loading .env.local first means its values win, and .env only fills the gaps. That is the file Vercel and Neon write when you pull env, so local overrides beat committed defaults.

Nothing else here decides anything. Move on.

ours scripts/eval.ts

main(): three modes, and the exit code is the gate core

pnpm eval
Baseline. Rerank off. Exits 1 on failure.
pnpm eval --rerank
Same, with the reranker on. Exits 1 on failure.
pnpm eval --compare
Runs both, prints the difference. Always exits 0.

L57 is the single most important line in the file. Architecture says "do not advance a tier until its evals pass." A rule like that is only real if a machine can enforce it, and the way a machine enforces it is a non-zero exit code that fails a CI job. Everything upstream exists to compute one boolean, summary.passed, and this line turns it into a signal the shell understands.

L50 is the deliberate exception. Compare mode is a measurement, not a gate. It answers "does the reranker earn its place?" by running the identical suite twice with one variable flipped, L45 and L46. You read the lift, you decide. It would be wrong for a measurement to fail the build.

Why run them one after the other instead of in parallel? Each suite already runs three cases at once, and each case is one generation plus eight judge calls. Two suites at once would double that load on a single gateway key, and one rate-limit error would kill both runs with nothing to show. Compare mode is slow and that is fine.

The rerank flag is passed all the way down to retrieve(). It is the only knob. If the two runs differ, the reranker is the only thing that could have caused it, modulo judge noise.

ours scripts/eval.ts

The printers: formatting, nothing decided here glue

Scores live as fractions in 0 to 1 and are shown as percentages. Lift is shown in percentage points, so "+6.2pt" means the mean went from, say, 0.700 to 0.762.

The one thing worth noticing is L23 and L34: neither printer knows the names of the three axes. They loop over AXES, a small table exported from summary.ts. Add a fourth axis in that table and the printers, the means, and the failure check all pick it up. That is the DRY rule from the project instructions applied to something that would otherwise be hard-coded in five places.

The "graded 8/11" fragment tells you how many cases went to the judge (answerable ones) out of the total. If that ever reads 11/11 or 0/11, the golden set has lost one of its two halves and the guard on slide 9 should have caught it.

ours src/server/evals/run.ts

runEvalSuite(): validate, fan out, summarize core

This is the whole suite in four statements. Pick the cases, check them, run each one with a concurrency cap, hand the list of results to the pure summarizer.

L9 TOP_K = 5 mirrors what ask() passes in production. If production ever changes its top-K and this constant does not, the eval silently grades a different system. That is the kind of drift the next slides are designed to prevent, and this is the one number that is duplicated rather than shared. Worth knowing.

L60 runs the guard before spending any money. A malformed golden set fails in a millisecond instead of after eleven model calls.

L61 defaults rerank to false deliberately, not to the environment flag. The eval must be explicit about which variant it is measuring. Production reads RERANK_ENABLED; the eval never does.

The cases and concurrency overrides exist so a future test or a smaller smoke run can pass three cases and concurrency one without touching the file. Nothing calls them today.

ZERO_SCORES is used on the next-but-one slide. It is the score sheet for an answerable question the model wrongly refused: all zeros, so the refusal costs as much as the worst possible answer.

production util, reused

mapPool(): three cases in flight, fail fast glue

A plain Promise.all(cases.map(runCase)) would launch all eleven cases at once. Each case is roughly one embedding call, two SQL queries, one generation, and eight judge calls. Eleven at once is about a hundred requests hitting one gateway key in the same second. The pool caps that at three workers pulling from a shared cursor, L31.

Results land at their original index, L31, so the output order matches the golden set even though completion order does not. The summarizer does not care about order, but a human reading a future per-case dump will.

L33 and L34: the first error flips a flag and every other worker stops picking up new work. Without that, a dead database or an exhausted quota would keep burning model calls for cases whose results are already lost.

L23 clamps a bad limit (zero, negative, NaN) to at least one worker so the pool can never return an array of holes without calling the function.

This file is not eval code. The same helper drives channel ingest. It is here because the harness reuses it rather than writing a second one.

ours src/server/evals/golden.ts

The golden set: eleven questions, no answers core

Look at the type. There is a query. There is no expectedAnswer. Slide 1 said the judge checks properties, not correctness, and here is the structural proof: the data does not contain what a correctness check would need.

The one bit that is labelled by a human is L17, expectRefusal. It splits the set into two kinds of case that are graded completely differently:

  • Answerable (8 cases). The corpus covers it. The model should answer, and the answer goes to the three judges.
  • Refusal (3 cases). The corpus does not cover it. The only correct output is the exact refusal sentence. No judge is involved; the decision itself is the grade.

Why put refusal cases in at all? Because "the refusal is the product" (DESIGN.md §1). A model that confidently answers a question about Bitcoin from a 2005 speech is hallucinating, and no amount of faithfulness scoring on the other eight questions would reveal it. The refusal cases are the only thing that tests the boundary of the corpus.

The three refusal probes are chosen to fail differently: crypto is plausible-sounding but anachronistic, lasagna is plainly off-topic, Android is on-brand (tech, Apple's rival) but still not in the speech. A model that refuses all three is refusing for the right reason, not because the question looked weird.

The corpus today is one stand-in video. When the full channel is ingested, this list is replaced. Every other file on these slides stays as it is.

ours src/server/evals/golden.ts

validateGolden(): the guard that keeps both halves alive glue

Four checks. The first three are ordinary hygiene: a non-empty list, non-blank queries, unique ids. The last two, L97 and L98, are the ones that protect the meaning of the score.

Think about what happens without them. Someone edits the golden set for a new channel and forgets to add refusal cases. The suite still runs. Refusal accuracy is computed over zero relevant cases and comes out as whatever the arithmetic gives, the means look fine, the gate says PASS. An entire axis has gone dark and nothing said so. The guard turns that silence into a thrown error before any model is called.

Same in the other direction: a set of only refusal cases would have every mean equal zero over an empty list, and the gate would fail for a reason that has nothing to do with the model.

The guard is exported and called from two places, the runner and the test file, so the committed set is checked on every pnpm test as well as every pnpm eval.

ours src/server/evals/run.ts

runCase(): one question through the real path, then a grading decision core

This is the function to understand completely. Everything before it is delivery; everything after it is arithmetic on what it returns.

Is this case marked expectRefusal?
yes → scores = undefined
Not judged. Only refused matters, and it is compared to expectRefusal later.
no → did the model refuse?
refused → ZERO_SCORES
Wrongful refusal. All three axes score 0, and it stays in the denominator.
answered → scoreAnswer()
The three Mastra judges run on the real answer.

Lines 29 to 33: produce the answer exactly as production would

L29 calls the same retrieve() that ask() calls, with the same topK of 5. The only addition is rerank, forwarded from the CLI flag. The result is a list of Evidence: chunk text (already widened with its ±1 neighbours), a score, and where in which video it came from.

L31 to L33: if retrieval came back empty, the answer is the refusal sentence without calling the model. That is a copy of the short-circuit in ask(), kept in step on purpose. Otherwise the agent is called with buildAnswerMessages(), the same prompt builder production uses, so the model sees a byte-identical user turn. Production streams; here we generate() and take .text, since there is nothing to stream to.

Line 35: one boolean that decides the rest

isRefusal() asks whether the whole answer is the refusal sentence, not whether it starts with it. The next slide shows why that strictness matters.

Lines 36 to 44: grade by the case's kind, not the model's choice

This nested ternary is the heart of the harness. Read it as the decision tree on the left.

The subtle branch is the middle one. An answerable case the model refused gets ZERO_SCORES, not undefined. If it were undefined, the summarizer would have to skip it, and then a model that refuses ten questions and answers one well would average 100%. Giving the refusal an explicit zero keeps it in the denominator and makes it cost exactly what a worthless answer costs.

The last branch hands the judges three things: the question, the answer, and evidence.map(e => e.text), the exact chunk texts the model read, in the exact order it read them. That order is what context precision grades.

L46 returns a tiny record. Four fields. Everything the summarizer needs and nothing it does not.

production, imported by the harness · src/server/answer.ts

The shared contract: one refusal string, one detector, one prompt core

One string, three readers

L10: the refusal sentence is defined once. The agent's system prompt interpolates it ("reply exactly: …"), ask() emits it when retrieval is empty, and the harness imports it to detect refusals. If someone rewords it in one place, the other two follow. If it were three literals, the eval would start counting real refusals as answers the day the copy changed.

Why equality, not "starts with"

L28 compares normalized whole strings. The normalization is just tolerance for cosmetics: surrounding quotes, whitespace, a trailing period or exclamation mark, case. It is not a prefix match, and that is the point. A prefix match would fail in both directions:

  • It would miss a correct refusal wrapped as "He doesn't cover that in his videos." with quotes, failing the gate on right behaviour. The normalizer handles that.
  • It would accept "He doesn't cover that in his videos, but he does say X [1]" as a refusal. That hedge is exactly what the system prompt forbids. Under equality it counts as an answer, goes to the judges, and faithfulness decides whether "X" was real.

Refusal accuracy is held at 100%, so this detector has to be right every time. That is why it is small and strict.

What the model actually sees

L44 builds the single user turn. Here is a real-shaped example for the calligraphy question, trimmed:

Evidence: [1] Steve Jobs' 2005 Stanford Commencement Address (at 3:12) …Because I had dropped out and didn't have to take the normal classes, I decided to take a calligraphy class to learn how to do this… [2] Steve Jobs' 2005 Stanford Commencement Address (at 4:05) …when we were designing the first Macintosh computer, it all came back to me. And we designed it all into the Mac… [3] … [4] … [5] … Question: What did dropping out let Steve Jobs study, and how did it shape the Mac?

The numbering is load-bearing. Marker [2] in the answer means evidence entry 2, which is citations[1] in the UI. The judges see the same texts, minus the numbers and titles, as plain context strings.

scoreAnswer(): what we hand Mastra, what we take back core

What goes in

model
L27 The judge. gateway(env.EVAL_MODEL), default zai/glm-5.3-flash, routed through the Vercel AI Gateway like every other model call. A separate knob from the generation model so you can make the judge stronger without touching production.
run.input
L28 The user's question, as a bare string.
run.output
L28 The model's answer, as a bare string, citation markers and all.
options.context
L33 L38 The evidence texts in ranked order. Given to faithfulness and context precision, which need to know what the model read. Answer relevancy does not take it: relevance to the question does not depend on evidence.

Mastra's scorers are built to grade agent traces, so they normally receive message arrays. Their input readers accept a plain string too, which is what we pass. That keeps our side to one line, L28, instead of building fake message objects.

What comes back

Each .run() resolves to a result object with a score in 0 to 1, a reason string written by the judge, and the intermediate step outputs (the extracted claims, the per-claim verdicts). L43 to L45 keep only the score. The reason is generated and then discarded. That is a cost we pay for nothing today, and the last slide comes back to it.

Why construct scorers per call

Context precision and faithfulness carry the context in their options, and the context is different for every question. So the scorer object has to be rebuilt each time. Construction is configuration only, no I/O, so this costs nothing measurable.

L30 runs the three in parallel. They are independent reads of the same answer.

Context precision throws at construction if the context array is empty. runCase() never reaches scoreAnswer() with empty evidence, because empty evidence becomes the refusal, and refusals never get judged. The invariant is upstream, which is why there is no guard here.
inside mastra @mastra/core/evals · @mastra/evals

Inside a Mastra scorer: four named steps, two or three of them are LLM calls

A prebuilt scorer is a small pipeline declared with a builder. .run() compiles it into a Mastra workflow and executes the steps in order. Each step that is defined as a prompt goes to a judge agent whose reply is forced into a JSON schema.

The four steps

StepKindPurpose
preprocessLLMBreak the answer into atomic units (claims or statements). Output forced to { claims: string[] }.
analyzeLLMGive each unit a verdict. Output forced to a verdict array.
generateScoreplain codeTurn verdicts into one number. No model, so the arithmetic is deterministic given the verdicts.
generateReasonLLMWrite a sentence explaining the score. We never read it.

The judge, L464, is an ordinary Mastra Agent built from our model and a fixed system instruction per scorer. When a step has a createPrompt, the runtime sends that prompt to the judge with structuredOutput set to the step's schema, so the reply parses as JSON or the step fails. Nothing here is fuzzy string parsing.

L483: the analyze step receives results.preprocessStepResult, the output of the previous step. That is the whole data flow: each step sees the run plus everything before it.

L508: generateScore is a function, not a prompt. This is the property that makes the scores explainable on the next three slides. Given the verdicts, the number is arithmetic you can check by hand.

How many model calls per answerable case

faithfulness
3 (extract, verify, reason)
answer relevancy
3 (extract, judge, reason)
context precision
2 (judge, reason; it has no preprocess)
total judging
8 judge calls, plus the 1 generation that produced the answer

Eight answerable cases means roughly 64 judge calls per run, or about 128 for --compare. That is why the concurrency cap and the sequential compare mode exist.

inside mastra judge 1 of 3 · threshold 0.70

Faithfulness: is every claim in the answer backed by the evidence?

What it measures, in one sentence

The fraction of claims in the answer that the judge could point to in the evidence. Everything else, whether contradicted or merely unmentioned, counts as unsupported.

faithfulness = yes / (yes + no + unsure)

A worked example

Suppose Nexus answers the calligraphy question with this (illustrative, not a recorded run):

"Dropping out let him drop in on a calligraphy class at Reed [1]. He learned about serif and sans-serif typefaces and what makes great typography great [1]. Ten years later that came back when designing the first Macintosh, which became the first computer with beautiful typography [2]. Windows later copied the Mac's approach [2]."

Step 1 splits it into claims. Step 2 checks each against the five evidence texts:

yesDropping out let him take a calligraphy class at Reed.
yesHe learned about serif and sans-serif typefaces.
yesHe learned what makes great typography great.
yesTen years later it came back when designing the first Macintosh.
yesThe Mac was the first computer with beautiful typography.
unsureWindows later copied the Mac's approach. (true in the speech, but say chunk 2 was cut before that line, so the context does not contain it)
faithfulness = 5 / 6 = 0.83 → above the 0.70 bar

What to notice

  • Only "yes" counts. A claim the judge cannot find scores the same as one that is contradicted. This is strict on purpose: anything not in the evidence is, from the user's point of view, invented.
  • The evidence is what the model read, not the whole transcript. A true fact from elsewhere in the video that was not retrieved is still penalised. That is correct: the model could only have got it from outside knowledge, which the system prompt forbids.
  • Hedging is penalised. "He might have…" is marked unsure by rule. Nexus is told not to hedge, and this scorer agrees.
  • Citation markers ride along. The [1] tokens are just characters in the claim text. The judge ignores them; it checks the words.
  • Zero claims scores zero. An empty answer is not "trivially faithful", it is a fail. This never fires in practice because refusals are routed around the judge.
inside mastra judge 2 of 3 · threshold 0.70

Answer relevancy: does each sentence address the question asked?

What it measures, in one sentence

How much of the answer is spent answering the question, with partial credit for sentences that are on-topic but not a direct answer.

relevancy = (yes + 0.3 × unsure) / statements

The 0.3 is Mastra's default uncertaintyWeight. We do not override it.

Same example answer, different question asked of it

The judge now ignores the evidence entirely. It only has the question and the answer:

yesDropping out let him take a calligraphy class at Reed. Directly answers "what did dropping out let him study".
yesHe learned about serif and sans-serif typefaces and what makes typography great. Elaborates the "what he studied" half.
yesTen years later that came back when designing the first Macintosh. Directly answers "how did it shape the Mac".
unsureWindows later copied the Mac's approach. Related to the Mac's typography, but the question did not ask about Windows.
relevancy = (3 + 0.3 × 1) / 4 = 3.3 / 4 = 0.83

What to notice

  • Correctness is explicitly out of scope, in capital letters in the prompt. A confidently wrong sentence that addresses the question scores "yes" here. Faithfulness is the axis that would catch it. The two judges are designed not to overlap.
  • It punishes padding. Preamble like "Great question! Steve Jobs gave this speech in 2005…" is a "no" or "unsure" statement that dilutes the average. The system prompt says "be concise" and this is the number that checks it.
  • Splitting granularity affects the score. Step 1 is an LLM deciding where sentences break. The same answer can split into four statements one run and five the next, which moves the score slightly. This is the main source of run-to-run noise on this axis.
  • A refusal would score badly here, which is why refusals are never sent to this judge. "He doesn't cover that" is not relevant to "what does he say about connecting the dots". The harness grades refusals by the decision, not by prose.
inside mastra judge 3 of 3 · threshold 0.60 · the retrieval axis

Context precision: were the useful chunks ranked near the top?

The only score that looks at retrieval instead of generation, and the only one where order matters. This is the number the reranker is supposed to move, and the reason --compare exists.

What it measures, in one sentence

Walk down the ranked list. Every time you hit a useful chunk, note what fraction of the list so far was useful. Average those notes. Useful chunks at the top give high fractions; useful chunks buried under junk give low ones.

for each useful chunk at position i (1-based): precision@i = (useful chunks in positions 1..i) / i context precision = mean of precision@i over the useful chunks

Mastra's comments call it Mean Average Precision; with one query it is plain Average Precision. Same idea.

Four orderings of the same five chunks

Green is a chunk the judge marked useful. Position is the rank retrieve() gave it.

12345
(1/1 + 2/2) / 2 = 1.00 both useful chunks on top: perfect
12345
(1/1 + 2/3) / 2 = 0.83 one useful chunk slipped to third
12345
(1/2 + 2/3) / 2 = 0.58 junk on top: now below the 0.60 bar
12345
(1/3) / 1 = 0.33 one useful chunk, buried

What to notice

  • Same chunks, different order, different score. That is exactly what a reranker changes: it does not find new chunks, it reorders the fused top 20 before the cut to 5. If rerank on beats rerank off, it shows up here first.
  • Chunks below the last useful one do not matter. Y Y N N N and Y Y scored the same. Precision does not punish extra junk at the tail, only junk above a useful chunk.
  • "Useful" is defined relative to our answer, not to a gold answer. The prompt literally says "expected output" and we pass the generated answer. So a good chunk the model ignored can be marked "no". This is a real limitation and the honest reading is: the score measures how well retrieval fed the answer that was actually written.
  • The texts are the neighbour-expanded ones. Each context piece is the hit plus its ±1 neighbours, the same widened text the model saw. Order is the ranker's order: rerank score when on, RRF score when off.
  • No preprocess step. One judge call, then arithmetic. The cheapest of the three.
pure src/server/evals/summary.ts

The types and the bars: axes as data, thresholds as policy core

This file imports nothing. No model, no database, no env. That is a design decision, not an accident: the gate logic is the part most worth unit-testing, and it can only be unit-tested if it can run without a network.

AXES, the one table

L21 to L25 list the three axes with a key and a display label. The satisfies clause ties each key to AxisScores at compile time, so a typo in the table is a type error. The means loop, the failure loop, and both CLI printers iterate this table. It is the single place a fourth axis would be added.

CaseResult, the contract with runCase

L33 is what runCase() returns and what summarize() consumes. scores being optional, L37, encodes the rule from slide 10: present for every answerable case, absent for every expected-refusal case.

The bars

faithfulness ≥ 0.70
At most three in ten claims unsupported, on average.
answer relevancy ≥ 0.70
Most of every answer must be on-question.
context precision ≥ 0.60
Looser: retrieval noise is expected, and a stand-in corpus of one video makes every chunk topically close.
refusal accuracy = 1.00
Exact. One wrong refusal decision in eleven fails the run.

Why is refusal the only perfect bar? Because it is the only axis where a single miss is a product failure rather than a quality dip. One hallucinated Bitcoin opinion, shipped with a confident citation, costs more trust than a dozen slightly rambling answers. The thresholds are policy, passed as a default parameter, so a future stricter tier can raise them without touching the math.

pure src/server/evals/summary.ts

summarize(): two averages and a comparison, with one trap avoided core

The means: denominator is "should have answered", not "did answer"

L79 filters to answerable cases by the label, !expectRefusal. It does not filter by whether the model chose to answer. Combined with the zero scores from runCase(), L81 averages over all eight answerable questions every time.

Here is the trap that avoids. Imagine a model that refuses seven of the eight and answers one perfectly. If the average were over answered cases, it would score 1.0 on every axis and pass. Under this code its faithfulness mean is (1.0 + 7 × 0) / 8 = 0.125 and it fails hard. The ?? 0 on L81 is a belt to that suspenders: even if a future caller forgets the zero scores, a missing score sheet counts as zero, never as absent.

Refusal accuracy: one comparison catches both mistakes

L87 to L88: a decision is correct when refused === expectRefusal. That single equality covers both failure modes, over all eleven cases:

expectRefusalrefusedVerdict
truetruecorrect refused an out-of-corpus question
truefalsewrong answered something the corpus does not cover: hallucination risk
falsetruewrong refused something the corpus covers: lost coverage
falsefalsecorrect answered an answerable question

Note the third row is penalised twice: once here (refusal accuracy drops below 1.0) and once in the means (its zero score sheet). That is intentional. A wrongful refusal is both a wrong decision and a missing answer.

The gate

L92 and L94 collect every axis under its bar into failures. L101: passed means the list is empty. The names in the list are what the CLI prints after FAIL ✗, so a red run tells you which axis to look at, not just that something broke.

The mean() helper returns 0 for an empty list, so a set with zero answerable cases cannot divide by zero. The guard on slide 9 makes that set impossible anyway; this is defence in depth for a pure function that anyone might call.

The tests: what is pinned down without a network glue

Both files run under pnpm test in milliseconds. They never call a model, because the code under test never does.

summary.test.ts pins six behaviours

  • Means are over answerable cases and a clean run passes with an empty failure list.
  • A low mean fails and names the axis, and only that axis.
  • Both refusal failure modes drop refusal accuracy below 1.0.
  • A wrongful refusal counts as zero, not as un-graded. This is the one that protects against the "refuse everything but one" exploit. If someone later "simplifies" the summarizer to skip cases without scores, this test goes red.
  • An all-refusal input does not divide by zero.
  • The default refusal threshold is exactly 1.

golden.test.ts pins the data

  • The committed GOLDEN_SET passes its own guard, so a broken edit fails CI before anyone runs a paid eval.
  • Each of the guard's five error paths (empty set, duplicate id, blank query, no refusals, no answerables) is exercised with a two-line fixture.

What is not tested: runCase() and scoreAnswer(). They are thin wrappers over network calls, and testing them would mean mocking Mastra, the agent, and the database for little insight. The decisions they make (the ternary on slide 10) are exercised indirectly by the summary tests through the CaseResult shapes they produce.

How to read the lift

The lift block is the whole reason the reranker is allowed to exist. In the example the retrieval axis moves by double digits while the generation axes barely move. That is the expected shape: reranking reorders evidence, so context precision should move first and most. Small moves on faithfulness and relevancy are downstream of better evidence and partly judge noise.

If the lift were near zero, DESIGN.md §7 says the reranker does not earn its place and should be turned off or removed. The number decides, not the architecture diagram.

Exit codes

0
pnpm eval passed, or --compare finished (it always exits 0).
1
The gate failed, or something threw (database down, gateway quota, malformed golden set). Read the output above the exit to tell them apart.

Noise

Two consecutive runs on identical code will not print identical numbers. Generation is sampled, the judge is sampled, and statement splitting varies. With eight answerable cases, one case moving by 0.2 shifts a mean by 2.5 points. Treat differences under a few points as weather, not signal.

honest limits

What this harness does not tell you

None of these is a bug. Each is a trade the design made, and knowing them is what lets you read a PASS correctly.

Faithful to the wrong chunk still scores faithful. If retrieval returns a chunk about being fired and the model answers the calligraphy question from it, every claim can be "supported" while the answer is off. Context precision is the axis meant to catch that, which is why its threshold matters even though it is the loosest.
Context precision is graded against our own answer. "Useful for generating the expected output" uses the generated answer as the expected output. A good chunk the model ignored can be marked irrelevant, and a bad answer can make its own evidence look precise. The score is best read as "how well did retrieval feed what was written".
Judge and generator are the same default model. Both default to zai/glm-5.3-flash. Models tend to rate their own style favourably. EVAL_MODEL is a separate knob precisely so the judge can be made stronger or different; today it is not.
Eleven cases is a smoke test, not a benchmark. One case moving 0.2 shifts a mean 2.5 points. The gate is meaningful for catching regressions of the "it broke" kind, less so for ranking two close variants.
The judge's reasons are paid for and thrown away. Every scorer runs a generateReason call whose sentence we never read. On a failing run those sentences are exactly the debugging aid you would want. Nothing in the code surfaces them yet.
Completeness is not measured. A short, true, on-topic answer that omits half of what the speech says scores perfectly on all three axes. Mastra ships a context-recall scorer for that; Tier 1 chose not to use it.

What the harness does tell you, reliably: the model is not inventing claims beyond its evidence, it is answering the question it was asked, its retrieval puts useful material on top, and it refuses exactly where the corpus ends. For a Tier 1 gate, those are the right four things.
